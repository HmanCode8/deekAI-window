# 05 · 构建发布与开发指南

## 1. 目录结构

```
deekai-electron/
├─ src/
│  ├─ main/              # Electron 主进程
│  │  ├─ index.ts        # 窗口、单实例锁、协议注册、生命周期
│  │  ├─ ipc.ts          # 全部 IPC handler（薄适配层）
│  │  ├─ config.ts       # 桌面端配置管理器（ConfigCore 的薄封装）
│  │  └─ deeplink.ts     # deekai:// 协议注册与解析
│  ├─ preload/           # contextBridge，实现 DeekaiBridge
│  ├─ renderer/          # React UI（桌面端与网页端共用）
│  │  ├─ index.html      # 挂载点 + CSP
│  │  └─ src/
│  │     ├─ App.tsx      # 门控状态机 + hash 路由
│  │     ├─ components/  # Chat / SettingsDialog / ShareDialog / SharedView / Markdown
│  │     │  └─ settings/ # SettingsGeneralTab / SettingsModelsTab（按 Tab 拆分）
│  │     ├─ pages/       # Login / Onboarding

│  │     └─ styles/globals.css
│  ├─ backend/           # 纯 Node 能力层（无框架依赖）
│  │  ├─ deepseek.ts     # 模型流式对话（OpenAI 兼容，不认厂商）
│  │  ├─ models.ts       # 拉取 {baseUrl}/models 可用模型列表
│  │  ├─ uploads.ts      # 文件解析 / Files API

│  ├─ server/            # 网页端能力服务
│  │  ├─ index.ts        # Express、静态托管 out/web、SPA 回退、错误处理
│  │  ├─ router.ts       # HTTP 契约（6 个端点）
│  │  └─ config.ts       # 服务端配置管理器
│  └─ shared/            # 两端/三层共用
│     ├─ bridge-api.ts   # DeekaiBridge 契约、PublicConfig、ChatStreamEvent

├─ scripts/
│  ├─ gen-icon.js               # 纯 Node 生成 icon.png / icon.ico
│  ├─ build-server.mjs          # esbuild 打包网页端服务
│  └─ prepare-release-config.mjs# 打包前生成发行内置 app-config.json
├─ supabase/migrations/         # create_shared_conversations.sql
├─ electron-builder.yml         # 发行版打包配置
├─ electron-builder.advanced.yml# 自托管版打包配置
├─ electron.vite.config.ts      # 桌面端三进程构建
├─ vite.web.config.ts           # 网页端前端构建（含 /api 代理）
└─ app-config.example.json      # 发行内置配置示例
```

## 2. npm 脚本

| 脚本 | 作用 |
|---|---|
| `dev` | Electron 开发模式（`electron-vite dev`，渲染层 HMR） |
| `build` | 构建桌面端三进程到 `out/` |
| `start` | 预览构建产物（`electron-vite preview`） |
| `dev:web` | 并行启动网页前端（Vite，5174）与能力服务（tsx，8787） |
| `build:web` | 构建网页端：`vite build` → `out/web` + esbuild → `out/server/index.cjs` |
| `start:web` | 运行网页端服务（`node out/server/index.cjs`） |
| `build:server` | 只打服务端产物 |
| `typecheck` | `typecheck:node` + `typecheck:web`（两个 tsconfig 分别检查） |
| `gen:icon` | 生成 `build/icon.png` 与 `build/icon.ico` |
| `prepare:release-config` / `prepare:advanced-config` | 生成 `build/app-config.json`（打包前注入用） |
| `dist:win` | 构建 + 注入发行配置 + 打 Windows 安装包（release） |
| `dist:win:advanced` | 同上，但用 `electron-builder.advanced.yml`（advanced） |

路径别名统一为 `@shared` → `src/shared`（三处配置都要同步：`electron.vite.config.ts`、`vite.web.config.ts`、`scripts/build-server.mjs`）。

## 3. 构建产物与打包

### 桌面端 `npm run build`
electron-vite 分别构建三个目标：

| 目标 | 入口 | 产物 |
|---|---|---|
| main | `src/main/index.ts` | `out/main/index.js` |
| preload | `src/preload/index.ts` | `out/preload/index.js` |
| renderer | `src/renderer/index.html` | `out/renderer/` |

### 打包 `npm run dist:win`
实际上是三步：

1. `npm run build` — 构建三进程；
2. `npm run prepare:release-config` — 读项目根的 `app-config.json`，强制写入 `DEEKAI_EDITION` 后输出到 `build/app-config.json`；
3. `electron-builder --win` — 打包。

`electron-builder.yml` 的关键点：
- `files` 只收 `out/**` + `package.json`，并排除 `src/**`、`out/web/**`、`out/server/**`、`*.map`；
- `extraResources` 把 `build/app-config.json` 放到安装目录的 `resources/app-config.json`（这就是"发行内置配置"的落地方式）；
- `electronDist: node_modules/electron/dist` 直接用本地已下载的 Electron，避免打包时重复下载；
- 目标是 NSIS 安装包（`oneClick: false`，可选安装目录、建桌面快捷方式）+ Portable 免安装版；
- 产物名：`DeekAI-Setup-<version>.exe`、`DeekAI-Portable-<version>.exe`（advanced 版前缀变 `DeekAI-Advanced-`）。

> 打包脚本会在 release 版缺少 `SUPABASE_URL` / `SUPABASE_ANON_KEY` 时打印警告——这表示打出来的包用户装完只能进内存模式。

### 图标生成 `npm run gen:icon`
`scripts/gen-icon.js` 是**零原生依赖**的纯 Node 光栅化：

- 用 SDF（圆角矩形 / 胶囊 / 三角形）描述图形，逐像素算覆盖率做抗锯齿；
- 输出 `build/icon.png`（512，开发时窗口图标）与 `build/icon.ico`（16/32/48/128/256）；
- ICO 用标准 **32 位 BMP(DIB) 条目 + AND 掩码**组装（不用 PNG 压缩条目，兼容性更好）。

两个易踩的坑：
1. 几何量与采样点必须**在同一坐标系**（都乘/都不乘缩放系数）——否则只有 512 尺寸是对的，小尺寸会把图形挤进角落变成全透明；
2. Windows 会缓存图标，替换安装包后如果看到的还是旧图标，先刷新资源管理器或删掉旧文件。

## 4. 网页端部署

```bash
npm ci --omit=dev          # 只装运行期依赖
npm run build:web          # 产出 out/web + out/server/index.cjs
# 准备 app-config.json 或 .env（见 04 篇）
node out/server/index.cjs  # 或 npm run start:web
```

服务端行为（`src/server/index.ts`）：
- `/api` 挂路由；
- 若 `out/web` 存在则静态托管，非 `/api` 的 GET 请求回退到 `index.html`（SPA 路由）；
- 统一错误处理返回 500 + `{error}`；
- 端口 `SERVER_PORT ?? PORT ?? 8787`。

托管平台若用 `PORT` 注入端口也能直接适配；本地开发时 Vite 代理读的是同一套变量，两边定义已统一。

## 5. 本地开发要点

### 桌面端
- `npm run dev`：主进程改动需要重启，渲染层有 HMR。
- 非打包运行时 `userData` 指向项目内 `.dev-profile`，配置和缓存都在那里。
- 想在开发时验证"发行版体验"，保留项目根的 `app-config.json` 即可；想恢复完整设置面板，加 `.env` 写 `DEEKAI_EDITION=advanced`。

### 网页端
- `npm run dev:web` 同时起两个进程：Vite（5174）与 tsx 跑的能力服务（8787）。
- 前端所有 `/api/*` 由 Vite 代理到 8787（见 `vite.web.config.ts`）。
- 改服务端代码需要重启 `dev:web`（tsx 未开 watch）。

### 类型检查
`npm run typecheck` 会分别跑两个 tsconfig：
- `tsconfig.node.json`：主进程 / preload / server / backend / shared
- `tsconfig.web.json`：renderer / shared

## 6. 扩展指南：新增一个后端能力

假设要加一个"生成会话摘要"的能力，改动顺序如下：

1. **能力层**：在 `src/backend/` 写纯逻辑函数（不依赖 Electron / Express）。
2. **共享契约**：在 `src/shared/bridge-api.ts` 的 `DeekaiBridge` 接口加方法签名（含入参/返回类型）。
3. **桌面端**：`src/main/ipc.ts` 注册 `ipcMain.handle("xxx:yyy", ...)`；`src/preload/index.ts` 在 bridge 对象里加一行转发。
4. **网页端**：`src/server/router.ts` 加一个端点；`src/renderer/src/lib/bridge/http.ts` 实现同一个方法。
5. **门面**：`src/renderer/src/lib/api.ts` 导出新函数。
6. **UI**：在组件里通过 `api.*` 调用——**不要**在组件里判断运行形态，除非确实需要差异化（例如桌面端才有的入口用 `api.bridgeKind` 判断）。

只要这 6 步走完，两端功能自动对齐。如果目标是换成 Java 后端，只需按 `router.ts` 注释里的 6 个端点契约重写 HTTP 层，前端与 `src/backend` 的实现细节都不用动。

> 如果新增的能力需要"多条配置"（像模型条目那样），建议照抄 `model-profiles.ts` 的模式：定义一个带 id 的条目结构 + 一个 `ModelTarget` 形态的"调用目标"（运营方预置 vs 调用方内联），运营方预置的条目走 `config-core` 的只读键与下发（`toPublicProfile` 脱敏），用户自己的条目走渲染层 `lib/model-profiles.ts` 的 `localStorage` 按账号分键 + 后端 `sanitizeModelTarget() / toResolvedModel()` 解析。这样"共享只读 + 用户私有"的权限模型、脱敏下发、按账号隔离都能直接复用。将来的智能体 / MCP / Skill 都可以按这个套路扩展。

## 7. 常见问题与坑

| 现象 | 原因与处理 |
|---|---|
| 网页端页面能开，但 `/api/config` 返回 **500** | 500 是 Vite 代理报的，说明 8787 的能力服务没应答。先 `netstat -ano \| findstr 8787` 看端口；多半是上一次的 node 子进程还占着端口（`Ctrl+C` 只杀了 npm 外壳没杀子进程），`taskkill /PID <pid> /F` 清掉再重启 |
| 设了 `SERVER_PORT` 却代理到别处 | 已统一为 `SERVER_PORT ?? PORT ?? 8787`（服务端与 Vite 代理同一套）。若你改过其中一处，注意保持一致 |
| 打包时报 `EPERM: mkdir 'C:\Users\...\AppData\Local\electron-builder'` | electron-builder 的缓存目录被限制。设置环境变量 `ELECTRON_BUILDER_CACHE=<项目内目录>` 后重跑 |
| `Error: Electron uninstall` | Electron 二进制没装好，设置 `electron_config_cache=<项目内目录>` 后执行 `node node_modules/electron/install.js` |
| 本地开发看不到 Supabase 配置项 | 项目根有 `app-config.json`（release）。加 `.env` 写 `DEEKAI_EDITION=advanced` |
| 桌面端生成的分享链接打不开 | 桌面端没有网页地址，需要配 `PUBLIC_WEB_URL` 才能拼出可访问链接 |
| 安装包/可执行文件图标是空白 | 图标生成脚本的坐标系数不一致（已修复）；另外注意 Windows 图标缓存 |
| 上传图片报"当前模型服务不支持图片上传" | 图片走 Files API，只有 DeepSeek 官方地址支持。改用文档附件，或把 Base URL 换回官方 |
| 改完配置没生效 | 设置面板保存后会 `location.reload()`；若改的是 `app-config.json` / `.env`，需要重启应用或服务 |
| 会话数据"莫名丢了" | 见 [03 篇 §4](./03-数据与账号体系.md#4-持久化策略重要影响数据安全)：写库是整表替换，多设备/多标签页同时用会互相覆盖 |
