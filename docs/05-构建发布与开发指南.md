## 2. npm 脚本

| 脚本 | 作用 |
|---|---|
| `dev` | Electron 开发模式（`electron-vite dev`，渲染层 HMR） |
| `build` | 构建桌面端三进程到 `out/` |
| `start` | 预览构建产物（`electron-vite preview`） |
| `dev:web` | 并行启动网页前端（Vite，5174）与能力服务（tsx，8787） |
| `build:web` | 构建网页端：`vite build` → `out/web` + esbuild → `out/server/index.cjs` |
| `start:web` | 运行网页端服务（`node out/server/index.cjs`） |
| `build:server` | 只打服务端产物 |
| `typecheck` | `typecheck:node` + `typecheck:web`（两个 tsconfig 分别检查） |
| `gen:icon` | 生成 `build/icon.png` 与 `build/icon.ico` |
| `prepare:release-config` / `prepare:advanced-config` | 生成 `build/app-config.json`（打包前注入用） |
| `dist:win` | 构建 + 注入发行配置 + 打 Windows 安装包（release） |
| `dist:win:advanced` | 同上，但用 `electron-builder.advanced.yml`（advanced） |

路径别名统一为 `@shared` → `src/shared`（三处配置都要同步：`electron.vite.config.ts`、`vite.web.config.ts`、`scripts/build-server.mjs`）。

## 3. 构建产物与打包

### 桌面端 `npm run build`
electron-vite 分别构建三个目标：

| 目标 | 入口 | 产物 |
|---|---|---|
| main | `src/main/index.ts` | `out/main/index.js` |
| preload | `src/preload/index.ts` | `out/preload/index.js` |
| renderer | `src/renderer/index.html` | `out/renderer/` |

### 打包 `npm run dist:win`
实际上是三步：

1. `npm run build` — 构建三进程；
2. `npm run prepare:release-config` — 读项目根的 `app-config.json`，强制写入 `DEEKAI_EDITION` 后输出到 `build/app-config.json`；
3. `electron-builder --win` — 打包。

`electron-builder.yml` 的关键点：
- `files` 只收 `out/**` + `package.json`，并排除 `src/**`、`out/web/**`、`out/server/**`、`*.map`；
- `extraResources` 把 `build/app-config.json` 放到安装目录的 `resources/app-config.json`（这就是"发行内置配置"的落地方式）；
- `electronDist: node_modules/electron/dist` 直接用本地已下载的 Electron，避免打包时重复下载；
- 目标是 NSIS 安装包（`oneClick: false`，可选安装目录、建桌面快捷方式）+ Portable 免安装版；
- 产物名：`DeekAI-Setup-<version>.exe`、`DeekAI-Portable-<version>.exe`（advanced 版前缀变 `DeekAI-Advanced-`）。

> 打包脚本会在 release 版缺少 `SUPABASE_URL` / `SUPABASE_ANON_KEY` 时打印警告——这表示打出来的包用户装完只能进内存模式。

### 图标生成 `npm run gen:icon`
`scripts/gen-icon.js` 是**零原生依赖**的纯 Node 光栅化：

- 用 SDF（圆角矩形 / 胶囊 / 三角形）描述图形，逐像素算覆盖率做抗锯齿；
- 输出 `build/icon.png`（512，开发时窗口图标）与 `build/icon.ico`（16/32/48/128/256）；
- ICO 用标准 **32 位 BMP(DIB) 条目 + AND 掩码**组装（不用 PNG 压缩条目，兼容性更好）。

两个易踩的坑：
1. 几何量与采样点必须**在同一坐标系**（都乘/都不乘缩放系数）——否则只有 512 尺寸是对的，小尺寸会把图形挤进角落变成全透明；
2. Windows 会缓存图标，替换安装包后如果看到的还是旧图标，先刷新资源管理器或删掉旧文件。

## 4. 网页端部署

### 4.1 构建（在开发机 / CI 上做，需要完整依赖）

```bash
npm ci                 # 注意：build:web 依赖 devDependencies（vite / esbuild / typescript），不能 --omit=dev
npm run build:web      # 产出 out/web（前端）+ out/server/index.cjs（服务端，已 bundle）
```

### 4.2 部署目录结构（服务端按 cwd 找文件，别拆开）

```
<部署目录>/
├─ out/
│  ├─ web/              前端静态资源
│  └─ server/index.cjs  能力服务（express 已 bundle 进去）
├─ package.json         readVersion() 读它的 version
├─ package-lock.json
└─ app-config.json 或 .env   基础设施配置（Supabase 等）
```

```bash
npm ci --omit=dev      # 运行期只需要 express / dotenv / multer / pdf-parse / mammoth / @supabase/supabase-js
node out/server/index.cjs   # 或 npm run start:web
```

要点：
- 服务端用 `process.cwd()` 定位 `out/web`、`app-config.json`、`.env`，**必须在部署目录内启动**；写成 `node /绝对路径/out/server/index.cjs` 而 cwd 不对会找不到前端。
- 端口 `SERVER_PORT ?? PORT ?? 8787`（云平台用 `PORT` 注入也能直接适配）。
- 配置优先级：启动环境变量 > `.env` > `app-config.json`；生产建议用平台的「环境变量」功能，别把密钥写进仓库里的文件。
- 静态托管 + SPA 回退由服务端自己做（非 `/api` 的 GET 统一返回 `index.html`），前面挂 Nginx / 网关只需转发到该端口，不用额外 rewrite。
- 部署完成后把域名写回 `PUBLIC_WEB_URL`（桌面端拼分享链接要用），改完重启服务。

### 4.3 首次部署 Supabase 要做的三件事

1. 建 `projects` / `conversations` 表并开启 RLS（见 [03 篇 §2](./03-数据与账号体系.md#2-表结构)）；
2. 跑仓库里的迁移脚本：`create_shared_conversations.sql`、`create_user_model_configs.sql`；
3. Authentication → Providers 启用 Email 登录（是否要邮箱验证由你决定，客户端两种都处理了）。

服务端行为（`src/server/index.ts`）：
- `/api` 挂路由；
- 若 `out/web` 存在则静态托管，非 `/api` 的 GET 请求回退到 `index.html`（SPA 路由）；
- 统一错误处理返回 500 + `{error}`；
- 配置了 Supabase 时，`/api/chat` 与 `/api/upload` 会校验 `Authorization: Bearer <token>`（见 [03 篇 §5](./03-数据与账号体系.md#会话有效期不让它一直挂着)）。

### 4.4 用 Docker + Nginx 部署（推荐）

**思路：本机构建，服务器只收产物。** 服务器上不跑 `vite`、不需要源码。

```
浏览器 → nginx（80/443，TLS + 托管前端静态文件）→ /api/ → deekai-api（Node:8787）
```

三个容器：`deekai-nginx`（TLS + 静态文件 + 反代）、`deekai-api`（能力服务）、`deekai-certbot`（证书续期）。

相关文件全部在 `deploy/` 下：[docker-compose.yml](../deploy/docker-compose.yml)、[Dockerfile](../deploy/Dockerfile)、[Dockerfile.dockerignore](../deploy/Dockerfile.dockerignore)、[nginx/templates/default.conf.template](../deploy/nginx/templates/default.conf.template)。

**① 本机构建 + 打包**（需要完整依赖，vite/esbuild 在 devDependencies 里）

```bash
npm ci
npm run build:web        # 产出 out/web 与 out/server/index.cjs

tar -czf deekai-web.tgz out/web out/server \
  package.json package-lock.json .env deploy
```

包里只有产物和部署目录，没有 `src/`、`scripts/`、`node_modules`。
（`.env` 在项目根，因为 compose 用它注入配置，见下面的路径约定。）

**② 上传**

```bash
ssh root@<服务器IP> "mkdir -p /opt/deekai"
scp deekai-web.tgz root@<服务器IP>:/opt/deekai/
```

**③ 先签发证书**（必须在 nginx 启动前做：standalone 模式要独占 80 端口）

```bash
ssh root@<服务器IP>
cd /opt/deekai && tar -xzf deekai-web.tgz && rm deekai-web.tgz
mkdir -p deploy/certbot/conf deploy/certbot/www

docker run --rm -p 80:80 \
  -v "$PWD/deploy/certbot/conf:/etc/letsencrypt" \
  certbot/certbot certonly --standalone --non-interactive --agree-tos \
  --email <你的邮箱> -d 101.33.122.209.sslip.io
```

**④ 启动**（在 `deploy/` 目录里执行）

```bash
cd /opt/deekai/deploy
docker compose up -d --build
docker compose ps                    # deekai-api / deekai-nginx / deekai-certbot 都应 Up
docker compose logs -f deekai-nginx
```

然后访问 `https://101.33.122.209.sslip.io`。

**路径约定**（compose 里的相对路径都是相对 `deploy/` 解析的）：

| compose 里的写法 | 实际位置 | 说明 |
|---|---|---|
| `context: ..` | 项目根 | 构建上下文要拿 `out/`、`package.json` |
| `env_file: ../.env` | 项目根 `.env` | 应用配置 + `SITE_ADDRESS` 只此一份 |
| `../out/web` | 项目根 `out/web` | 前端产物 |
| `../server-data` | 项目根 `server-data` | 容器唯一可写目录 |
| `./certbot/*`、`./nginx/templates` | `deploy/` 内 | 证书、ACME 校验、站点配置模板 |

**更新代码时**：本机 `npm run build:web` 重新打包 → scp → 服务器解包覆盖 → `cd deploy && docker compose up -d --build`。
只改了前端的话，`docker compose restart deekai-nginx` 就够（静态文件是挂载的，nginx 重新读盘即可）。

镜像里的两个取舍：
1. **用 Debian 而不是 Alpine**：路径与系统库更接近常规 Linux，本机构建产物与服务器环境差异更小；
2. **`npm ci --omit=dev --ignore-scripts`**：根 `postinstall` 是 `electron-builder install-app-deps`，容器里不需要；
   这几个运行期依赖没有原生编译，跳过脚本是安全的。

注意事项：
- 配置走 `.env`（`env_file` 注入 deekai-api），**不打进镜像**；`.dockerignore` 也排除了 `app-config.json` 与各类 `.env`；
- nginx 的 `server_name` 与证书路径由 `deploy/nginx/templates/*.template` 里的 `${SITE_ADDRESS}` 决定，
  官方镜像的入口脚本会做 envsubst（用 `NGINX_ENVSUBST_FILTER` 限定只替换这一个变量，避免误伤 `$host` / `$uri`）；
- nginx 配置里对 `/api/` **关闭了 `proxy_buffering`**：对话是 SSE 流式返回，一缓冲就会变成"整段一次性显示"；
- nginx 默认 `client_max_body_size` 是 1m，配置里已调到 70m，否则大文件上传会被 413 拦掉；
- **不要覆盖 nginx 服务的 `command` / `entrypoint`**：官方镜像的入口脚本只在第一个参数是
  `nginx` / `nginx-debug` 时才执行 `/docker-entrypoint.d/`，模板渲染就在里面。覆盖后会退回镜像
  自带默认配置，现象是 `/api/*` 全 404、80 不跳转、443 不监听。
- 证书续期后要让 nginx 加载新证书，二选一：
  1. 手动 `docker compose exec nginx nginx -s reload`；
  2. 宿主机 crontab 每周自动 reload：`0 4 * * 1 cd /opt/deekai && docker compose exec -T nginx nginx -s reload`。
- `deekai-api` 用 `expose` 而不是 `ports`，公网只能经 nginx 进来，8787 不暴露。
- **必须有 HTTPS**：浏览器只在安全上下文（https 或 `http://localhost`）提供 `crypto.randomUUID` / `clipboard`，
  而这两个 API 被用在「新建对话 / 添加模型 / 发送消息 / 复制」上（见 `Chat.tsx`、`lib/api.ts`、`SettingsModelsTab.tsx`），
  所以用 `http://<公网IP>:8787` 访问会直接报错、应用不可用。
- **只有公网 IP、没有域名**时不必买域名：用 [sslip.io](https://sslip.io) 把 IP 写成域名即可申请真证书：
  ```
  # 服务器 IP 是 203.0.113.7
  SITE_ADDRESS=203.0.113.7.sslip.io
  PUBLIC_WEB_URL=https://203.0.113.7.sslip.io
  ```
  前提是放行 80/443（云厂商安全组 + 本机防火墙）。sslip.io 配额紧张时可换 `nip.io`，写法一样。
- 想先快速验证整条链路，可以用 SSH 隧道走 localhost（不发证书，纯 HTTP，但算安全上下文）：
  `ssh -L 8787:127.0.0.1:8787 user@server`，然后浏览器开 `http://localhost:8787`。

## 5. 本地开发要点

### 桌面端
- `npm run dev`：主进程改动需要重启，渲染层有 HMR。
- 非打包运行时 `userData` 指向项目内 `.dev-profile`，配置和缓存都在那里。
- 想在开发时验证"发行版体验"，保留项目根的 `app-config.json` 即可；想恢复完整设置面板，加 `.env` 写 `DEEKAI_EDITION=advanced`。

### 网页端
- `npm run dev:web` 同时起两个进程：Vite（5174）与 tsx 跑的能力服务（8787）。
- 前端所有 `/api/*` 由 Vite 代理到 8787（见 `vite.web.config.ts`）。
- 改服务端代码需要重启 `dev:web`（tsx 未开 watch）。

### 类型检查
`npm run typecheck` 会分别跑两个 tsconfig：
- `tsconfig.node.json`：主进程 / preload / server / backend / shared
- `tsconfig.web.json`：renderer / shared

## 6. 扩展指南：新增一个后端能力

假设要加一个"生成会话摘要"的能力，改动顺序如下：

1. **能力层**：在 `src/backend/` 写纯逻辑函数（不依赖 Electron / Express）。
2. **共享契约**：在 `src/shared/bridge-api.ts` 的 `DeekaiBridge` 接口加方法签名（含入参/返回类型）。
3. **桌面端**：`src/main/ipc.ts` 注册 `ipcMain.handle("xxx:yyy", ...)`；`src/preload/index.ts` 在 bridge 对象里加一行转发。
4. **网页端**：`src/server/router.ts` 加一个端点；`src/renderer/src/lib/bridge/http.ts` 实现同一个方法。
5. **门面**：`src/renderer/src/lib/api.ts` 导出新函数。
6. **UI**：在组件里通过 `api.*` 调用——**不要**在组件里判断运行形态，除非确实需要差异化（例如桌面端才有的入口用 `api.bridgeKind` 判断）。

只要这 6 步走完，两端功能自动对齐。如果目标是换成 Java 后端，只需按 `router.ts` 注释里的 6 个端点契约重写 HTTP 层，前端与 `src/backend` 的实现细节都不用动。

> 如果新增的能力需要"多条配置"（像模型条目那样），建议照抄 `model-profiles.ts` 的模式：定义一个带 id 的条目结构 + 一个 `ModelTarget` 形态的"调用目标"（运营方预置 vs 调用方内联），运营方预置的条目走 `config-core` 的只读键与下发（`toPublicProfile` 脱敏），用户自己的条目走渲染层 `lib/model-profiles.ts` 的 `localStorage` 按账号分键 + 后端 `sanitizeModelTarget() / toResolvedModel()` 解析。这样"共享只读 + 用户私有"的权限模型、脱敏下发、按账号隔离都能直接复用。将来的智能体 / MCP / Skill 都可以按这个套路扩展。

## 7. 常见问题与坑

| 现象 | 原因与处理 |
|---|---|
| 网页端页面能开，但 `/api/config` 返回 **500** | 500 是 Vite 代理报的，说明 8787 的能力服务没应答。先 `netstat -ano \| findstr 8787` 看端口；多半是上一次的 node 子进程还占着端口（`Ctrl+C` 只杀了 npm 外壳没杀子进程），`taskkill /PID <pid> /F` 清掉再重启 |
| 设了 `SERVER_PORT` 却代理到别处 | 已统一为 `SERVER_PORT ?? PORT ?? 8787`（服务端与 Vite 代理同一套）。若你改过其中一处，注意保持一致 |
| 打包时报 `EPERM: mkdir 'C:\Users\...\AppData\Local\electron-builder'` | electron-builder 的缓存目录被限制。设置环境变量 `ELECTRON_BUILDER_CACHE=<项目内目录>` 后重跑 |
| `Error: Electron uninstall` | Electron 二进制没装好，设置 `electron_config_cache=<项目内目录>` 后执行 `node node_modules/electron/install.js` |
| 本地开发看不到 Supabase 配置项 | 项目根有 `app-config.json`（release）。加 `.env` 写 `DEEKAI_EDITION=advanced` |
| 桌面端生成的分享链接打不开 | 桌面端没有网页地址，需要配 `PUBLIC_WEB_URL` 才能拼出可访问链接 |
| 安装包/可执行文件图标是空白 | 图标生成脚本的坐标系数不一致（已修复）；另外注意 Windows 图标缓存 |
| 上传图片报"当前模型服务不支持图片上传" | 图片走 Files API，只有 DeepSeek 官方地址支持。改用文档附件，或把 Base URL 换回官方 |
| 改完配置没生效 | 设置面板保存后会 `location.reload()`；若改的是 `app-config.json` / `.env`，需要重启应用或服务 |
| 会话数据"莫名丢了" | 见 [03 篇 §4](./03-数据与账号体系.md#4-持久化策略重要影响数据安全)：写库是按字段增量 + messages 乐观锁；只有「两端同时改写同一会话的历史消息」需要用户裁决一次 |
| 另一端改了数据但这边不刷新 | 检查 `conversations` / `projects` 是否在 `supabase_realtime` 复制里（`supabase/migrations/enable_chat_realtime.sql`）；订阅不通时会退化为「切窗口刷新」 |
| 提示「无法自动合并，要保留哪一份」 | 两端同时改写了同一会话的历史消息。这是预期行为，不是 bug；选一边即可，另一边的内容不会静默丢失（见 03 篇 §4.2） |
