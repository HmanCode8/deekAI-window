# 04 · 配置体系与版本

配置体系要同时解决两个互相冲突的需求：

1. **普通用户不该看到、也改不动后端基础设施**（Supabase 地址、Key 这类东西不可能让用户填）；
2. **用户需要能配自己的模型 Key**（BYOK）；
3. **开发者/自托管者要能改一切**。

解法是**三层配置 + 两类版本（edition）**。

## 1. 三层配置

| 层 | 来源 | 谁维护 | 桌面端位置 | 网页端位置 |
|---|---|---|---|---|
| `published` 发行内置 | `app-config.json` | 你（运营方），随包下发 | 安装目录 `resources/app-config.json` | 项目根 `app-config.json` |
| `base` 部署环境 | `.env` 文件 + 进程环境变量 | 部署方 | `<应用目录>/.env`、`resources/.env`、`cwd/.env` | `cwd/.env`、`cwd/.env.local` |
| `override` 用户设置 | `config.json` | 使用者（设置面板写入） | Windows：`%APPDATA%\<应用名>\config.json`（发行版为 `DeekAI`，开发时是 `deekai-desktop`） | `<dataDir>/config.json` |

核心逻辑集中在 `src/shared/config-core.ts` 的 `ConfigCore` 类，桌面端（`src/main/config.ts`）与网页端（`src/server/config.ts`）都只是**薄封装**——各自负责把"路径"和"发行内置配置"喂进去，合并/校验/脱敏逻辑完全共用。

> 桌面端非打包运行时，`userData` 会被改到项目内的 `.dev-profile`，所以开发时用户配置在 `<项目>/.dev-profile/config.json`。

## 2. 两类配置键

```ts
// 基础设施键（运营方）：普通用户不可见、不可改；advanced 自托管可在应用内改
INFRA_KEYS = [DATA_STORE, SUPABASE_URL, SUPABASE_ANON_KEY,
              SUPABASE_SERVICE_ROLE_KEY, PUBLIC_WEB_URL]

// 运营方模型键（运营方预置的"兜底/共享"条目）：只读，使用者改不了
OPERATOR_MODEL_KEYS = [DEEPSEEK_API_KEY, DEEPSEEK_BASE_URL, DEEPSEEK_MODEL,
                       MODEL_PROFILES,          // 批量预置的条目（JSON 数组字符串）
                       DEFAULT_MODEL_PROFILE]   // 运营方指定的默认条目 id
```

`DEEPSEEK_*` 三个键的语义是**内置保底条目**：配置层把它们合成一条「DeepSeek（内置）」条目，永远排在列表里、不可删除。运营方还可以用 `MODEL_PROFILES` 批量预置更多共享条目（结构见 [model-profiles.ts](../src/shared/model-profiles.ts)）。

> **用户自己的模型条目不在这些键里**。它们存本机 `localStorage`（按账号分键 `deekai:models:<userId>`），登录后同步到 Supabase 表 `user_model_configs`（RLS 仅本人可读写）；调用模型时随请求以 `inline` 目标带给后端，**不写进服务端配置文件**（见第 5.5 节）。

### 取值优先级

| 键类别 | 优先级（左高右低） |
|---|---|
| 基础设施键（release） | 发行内置 → 部署环境 → 用户配置 |
| 基础设施键（advanced） | **用户配置** → 发行内置 → 部署环境 |
| 运营方模型键（两种版本一致） | 用户配置（兼容存量） → 发行内置 → 部署环境 |

（基础设施键在 `release` 下把"用户配置"放在最后，只是为兼容早期自托管用户留下的存量数据；正常不会有值。）

### 写白名单

`save()` 只接受当前版本允许的键，其余一律丢弃：

| edition | 可写键 |
|---|---|
| `release` | 无（模型条目也不再走这里，而是写客户端本地） |
| `advanced` | 仅 `INFRA_KEYS` |

**这就是"用户改不动后端配置"的实现机制**——即使有人在 release 版里手改 `config.json` 塞进 `SUPABASE_URL`，加载时也会被 `filterByKeys` 过滤掉，永远不会生效。模型键在任何版本下都不可通过 `save()` 写入。

另：设置面板提交**空字符串表示清除该键**（`save` 里执行 `delete`），"清除本机设置"就是一次全键传空串的操作（顺带清空本账号的本机模型条目）。

## 3. 两类版本（edition）

### 判定优先级

```
启动环境变量 DEEKAI_EDITION  >  .env 文件里的 DEEKAI_EDITION  >  app-config.json 的 DEEKAI_EDITION  >  "release"
```

默认 `release`——**宁可少给权限，也不能把内部配置暴露给普通用户**。

打包脚本 `scripts/prepare-release-config.mjs` 会强制把 `DEEKAI_EDITION` 写进生成的内置配置，避免忘记设置。

### 行为差异

| | `release` 发行版 | `advanced` 自托管版 |
|---|---|---|
| 面向 | 普通用户 | 你自己 / 自托管者 |
| 设置面板 | 账号 / 外观 / 模型设置（本机条目）/ 关于 | 额外含 **数据存储 / Supabase / 分享** |
| 控制字段 | `canEditInfra === false` | `canEditInfra === true` |
| 能改 Supabase | 否（白名单拦截） | 是 |
| 「关于」文案 | 「本版本已内置后端与站点配置，无需填写；如需自托管…设置 DEEKAI_EDITION=advanced 后启动。」 | 显示 `数据目录：…` |
| 打包产物 | `DeekAI-Setup-*.exe`（appId `com.deekai.desktop`） | `DeekAI-Advanced-Setup-*.exe`（appId `com.deekai.desktop.advanced`，可与发行版同机共存） |
| 输出目录 | `release/` | `release-advanced/` |

`canEditInfra` 由 `PublicConfig` 下发（`edition === "advanced"` 派生），设置面板只凭这一个字段决定是否渲染那三个分区。

### 本地开发怎么进 advanced 模式

因为项目根目录存在 `app-config.json`（`release`），本地 `npm run dev` / `npm run dev:web` 默认也是 release 模式，看不到 Supabase 配置。想调试完整面板，在项目根建一个 `.env`：

```
DEEKAI_EDITION=advanced
```

或临时用环境变量：`$env:DEEKAI_EDITION="advanced"; npm run dev:web`

## 4. 环境变量清单

完整清单见下表；项目根的 `.env` 里有可直接照抄的写法（该文件已被 gitignore）。

| 变量 | 用途 | 备注 |
|---|---|---|
| `DEEKAI_EDITION` | `release` / `advanced` | 见上 |
| `DEEPSEEK_API_KEY` | 模型 API Key | 留空则要求用户自带（BYOK） |
| `DEEPSEEK_BASE_URL` | 模型服务地址（OpenAI 兼容） | 默认 `https://api.deepseek.com` |
| `DEEPSEEK_MODEL` | 默认模型名 | 前端选择器有独立清单，此项作为兜底 |
| `DATA_STORE` | `memory` / `supabase` | 留空时：Supabase 配齐即 `supabase`，否则 `memory` |
| `SUPABASE_URL` | Supabase 项目地址 | |
| `SUPABASE_ANON_KEY` | 公开 key，前端可见 | |
| `SUPABASE_SERVICE_ROLE_KEY` | 仅"老数据认领"用 | **桌面端不需要** |
| `PUBLIC_WEB_URL` | 网页端部署地址 | 用于拼分享链接 |
| `SERVER_PORT` / `PORT` | 网页端服务端口 | 默认 `8787`；Vite 代理读同一套变量 |
| `SERVER_DATA_DIR` | 网页端可写目录 | 默认 `./server-data` |
| `SERVER_CONFIG_PATH` | 网页端用户配置文件路径 | 默认 `<dataDir>/config.json` |

**存储模式的实际判定**（`computeStore()`）：

```
DATA_STORE === "memory"                      → memory
DATA_STORE === "supabase" 或留空              → SUPABASE_URL 与 ANON_KEY 都在 ? supabase : memory
其他值                                        → memory
```

## 5. 模型接入：多条目 + 任意 OpenAI 兼容服务

### 一条模型配置是什么

```ts
interface ModelProfile {
  id: string;          // uuid（内置条目的 id 固定为 "builtin-deepseek"）
  name: string;        // 自定义显示名，例如「我的 GPT-4o」
  providerId: string;  // 厂商预设 id（deepseek / openai / ... / custom）
  baseUrl: string;     // OpenAI 兼容根地址
  model: string;       // 厂商真实模型名
  apiKey: string;      // 该条目自己的 Key
}
```

存储位置分两类：

- **运营方条目**（内置保底 + `MODEL_PROFILES` 预置）：来自 `app-config.json` / `.env`，对所有使用者可见，**只读**；
- **用户自己的条目**：存在客户端本地 `localStorage` 的 `deekai:models:<userId>`（匿名/内存模式是 `deekai:models:local`），可增删改，**只有本账号可见**。

**Key 不回显**：
- 运营方条目下发渲染进程时（`PublicModelProfile`）不含 `apiKey`，只有 `hasKey` 布尔值，所以对用户永远是「只读 + 是否已配置」；
- 用户自己的条目存在本机、由本人维护，Key 就地明文保存（与头像、侧栏折叠状态同级），不经过服务端。

### 解析成运行时信息

后端不直接读配置，而是拿一个已经解析好的 `ResolvedModel`：

```ts
resolveModel(profileId) => {
  id, name, providerId, baseUrl, model, apiKey,
  supportsFiles,   // 是否可上传图片（Files API）
  visionModel,     // 需要读图时改用哪个模型（不需要则为 null）
}
```

选条目的顺序：**显式传入的 id → `DEFAULT_MODEL_PROFILE` → 第一个配好 Key 的条目 → 内置条目**。传入的 id 不存在时会静默回退，所以"切换了模型但配置被删掉"不会直接报错。

### 调用目标：ModelTarget（Key 归属的两种形态）

前端发起对话 / 上传时带的不是"条目 id"，而是统一的 `ModelTarget`：

```ts
type ModelTarget =
  | { kind: "profile"; profileId }                          // 用服务端/运营方条目，Key 留在服务端
  | { kind: "inline"; name?, providerId?, baseUrl, model, apiKey }  // 用调用方本机条目，Key 随请求带上
```

后端在边界处用 `sanitizeModelTarget()` 只信任形状合法的数据，再用 `toResolvedModel()` 解析成后端需要的 `ResolvedModel`：
`profile` 类型交给配置层按 id 查表；`inline` 类型直接用请求里带的地址与 Key，**不落盘**。

这样两种来源共用同一套调用链，后端代码不需要知道条目是从哪来的。

### 5.5 按用户隔离

模型清单天然分成两层，互不干扰：

| | 运营方条目 | 用户条目 |
|---|---|---|
| 来源 | `app-config.json` / `.env` | 本机 `localStorage` + 云端 `user_model_configs` |
| 存储键 | 实例配置（服务端磁盘） | `deekai:models:<userId>` / `deekai:models:local` |
| 可见范围 | 所有使用者（共享） | 仅本账号 |
| 可编辑 | 否（只读，带锁标记） | 是（增删改） |
| 跨设备 | 随部署/安装包 | 登录后同步：同一账号在网页端 / 桌面端 / 其他电脑都一致 |
| 调用时 | `{ kind: "profile", profileId }` | `{ kind: "inline", baseUrl, model, apiKey }` |

要点：
- 未登录（或未配置 Supabase）时用户条目只存本机；登录后以云端为准，本机留一份做即时可用与离线兜底；
- 登录前在登录页配的匿名条目会被并入账号并上传，不会白配；
- **云端那张表存了用户的 API Key**，所以 RLS 用一条 `for all ... using (auth.uid() = user_id)` 锁死本人，不能开放匿名读；
- 运营方条目永远只读，用户改不了；用户想加自己的就「添加模型」，存的是用户条目。

### 协议：全部按 OpenAI 兼容处理

```
对话：POST {baseUrl}/chat/completions     body: { model, messages, stream: true }
列表：GET  {baseUrl}/models               （设置面板的「从服务端获取」用）
图片：POST {baseUrl}/files                （仅 supportsFiles 为真的条目）
```

新增一个厂商只需要在 `PROVIDER_PRESETS` 里加一条预设（label / baseUrl / 常见模型），业务代码一行都不用改；如果该厂商是闭源协议，就选「自定义」让用户手填。

### 图片附件的能力门控

只有 DeepSeek 官方提供 Files API，所以：

- 条目带 `supportsFiles: true` → 可上传图片，UI 的文件选择器包含图片类型；
- 否则 → 文件选择器不列图片类型，且**在本地就把选中的图片拦下来**并提示改用文档类附件（避免白传一趟再报错）。

文档类附件（PDF / DOCX / 文本）走本地解析，与厂商无关，所有条目都能用。

### 模型选择顺序

```
消息里含图片附件 且 条目有 visionModel  →  改用该条目的视觉模型（目前仅 DeepSeek）
否则                                   →  条目自己的 model（为空则回落到第一个内置模型）
```


## 6. 前端能看到的配置（PublicConfig）

渲染进程调 `getConfig()` 拿到的只有这些，**不含任何密钥**：

| 字段 | 说明 |
|---|---|
| `store` | 实际生效的存储模式 |
| `supabaseConfigured` | URL + anon key 是否齐全 |
| `supabaseUrl` / `supabaseAnonKey` | 公开值（前端要直连 Supabase） |
| `serverModelProfiles` | 运营方预置的模型条目（**不含 Key，只有 `hasKey` 布尔值**），只读；用户自己的条目不在其中 |
| `publicWebUrl` | 分享站点地址 |
| `edition` / `canEditInfra` | 版本与权限 |
| `configSource` | 配置来源说明，如「发行内置配置 + 用户设置」 |
| `appVersion` / `userDataDir` | 版本号与数据目录（关于分区展示） |

运营方条目的 `API Key` 永不回显，设置面板里只显示「只读」；用户自己的条目存在本机，就在本机明文编辑与保存（见第 5.5 节）。

## 7. CSP 与网络白名单

`src/renderer/index.html` 内联了 CSP：

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self' data: blob: https:; font-src 'self' data:;
connect-src 'self' ws: http://localhost:* http://127.0.0.1:*
            https://*.supabase.co https://api.deepseek.com
```

需要注意的两点：

1. **渲染进程不直连模型服务**，模型请求由主进程/服务端发出，所以换 `DEEPSEEK_BASE_URL` **不需要**改 CSP。
2. 渲染进程要直连 Supabase，`connect-src` 里放的是 `https://*.supabase.co`。**如果你用自建域名 / 非 supabase.co 域名的 Postgres 网关，必须同步改这里**，否则请求会被浏览器拦掉。
3. `img-src` 里的 `blob:` 与 `data:` 是为头像与附件预览准备的；头像走的是 `data:`（`FileReader`），刻意避开了 blob URL。

## 8. 常见配置场景

### 场景 A：发行版（给普通用户）
1. 在项目根新建 `app-config.json`，填 `SUPABASE_URL` / `SUPABASE_ANON_KEY`（可选 `PUBLIC_WEB_URL`）。
2. `DEEKAI_EDITION` 留 `release`（打包脚本也会强制写入）。
3. 不填 `DEEPSEEK_API_KEY`（纯 BYOK），或填一个作为统一额度。
4. `npm run dist:win`。

### 场景 B：自托管自用
`.env` 里写 `DEEKAI_EDITION=advanced` + Supabase 三项（含 service_role）+ 自己的 Key，`npm run dev` 或 `npm run dist:win:advanced`。

### 场景 C：用户接入别的厂商（应用内，无需改代码）
打开「设置 → 模型设置」→「添加模型」：
1. 填显示名（例如「快速问答」）；
2. 选服务商（例如 OpenAI），Base URL 会自动带出 `https://api.openai.com/v1`；
3. 填该厂商的 API Key；
4. 模型下拉里选一个预设型号，或点「从服务端获取」拉真实列表，也可以直接手填；
5. 「确定」→「保存」，回到对话头部就能在模型下拉里看到它。
6. 保存的是**本机条目**（只有本账号可见，不出本机）；同页面的「内置模型」区是运营方预置的共享条目，只读。

想用 DeepSeek 以外、任何兼容 OpenAI 协议的服务（含本地 Ollama / vLLM / one-api 等中转），第 2 步选「自定义（OpenAI 兼容）」手填 Base URL 与模型名即可。

### 场景 E：运营方预置一条共享模型
在 `app-config.json`（发行版）或 `.env`（部署）里写 `DEEPSEEK_API_KEY` 或 `MODEL_PROFILES`，该条目会以「内置模型（只读）」出现在所有人的列表里；留空则不预置，由用户自带 Key（纯 BYOK）。
> 注意：这类条目是**全员共享**的。如果只是自己用，请在应用内「模型设置 → 添加模型」（本机条目），不要写进服务端配置。

### 场景 D：网页端部署
1. `npm ci --omit=dev`
2. `npm run build:web`（产出 `out/web` 与 `out/server/index.cjs`）
3. 准备好 `app-config.json` 或 `.env`
4. `npm run start:web`（或直接 `node out/server/index.cjs`），端口读 `SERVER_PORT ?? PORT ?? 8787`
5. 记得执行 `supabase/migrations/create_shared_conversations.sql`，并把部署域名写回 `PUBLIC_WEB_URL` 才能生成可用的分享链接。
