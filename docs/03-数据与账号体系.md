# 03 · 数据与账号体系

数据与账号全部托管在 **Supabase**（Auth + Postgres + RLS）。本应用**没有自建账号系统**，也不经手密码。

## 1. 三层数据职责

| 数据 | 存在哪 | 谁读写 |
|---|---|---|
| 账号、会话 token | Supabase Auth | 渲染进程（`supabase-js`），会话持久化到 `localStorage` 并自动续期 |
| 项目 / 会话 / 消息 | Supabase Postgres：`projects`、`conversations` | 渲染进程直连，`anon key + 用户 token`，RLS 隔离 |
| 分享快照 | Supabase Postgres：`shared_conversations` | 创建/撤销需登录，只读查看匿名即可 |
| 模型条目（用户自己的） | Supabase Postgres：`user_model_configs` + 本机 `localStorage` 缓存 | 渲染进程直连（RLS 按 `auth.uid()`）；未登录只存本机 |
| 后端配置（密钥等） | 本机 `config.json` / 服务端 `.env` / `app-config.json` | 主进程或服务端，渲染进程只能看到脱敏后的公开值 |
| 主题、头像、分享索引 | 浏览器 `localStorage` | 渲染进程 |

**关键点**：业务数据的读写完全由前端直连 Supabase 完成，Node 后端**不参与**会话/项目的增删改查。后端只在需要密钥或 Node 能力时才出场（调模型、解析文件、老数据认领）。

## 2. 表结构

### 2.1 `projects`（项目分组）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid / text | 主键，**由前端 `crypto.randomUUID()` 生成** |
| `name` | text | 项目名 |
| `sort_order` | int | 展示顺序，前端按数组下标写入 |
| `user_id` | uuid | 归属用户，列默认值 `auth.uid()` |

### 2.2 `conversations`（会话）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid / text | 主键，前端生成 |
| `project_id` | 同 projects.id，可空 | `null` 表示未分组 |
| `title` | text | 会话标题（首条消息前 20 字） |
| `messages` | jsonb | 消息数组，元素形如 `{ role, content, attachments? }` |
| `sort_order` | int | 展示顺序 |
| `user_id` | uuid | 归属用户，列默认值 `auth.uid()` |

> ⚠️ **这两张表的建表脚本不在本仓库**。本应用沿用网页版（Next.js 项目）同一个 Supabase 库，`projects` / `conversations` 及其 RLS 策略是网页版时代建的。若你要部署到一个全新的 Supabase 项目，需要先把这两张表建好并开启 RLS（按 `auth.uid() = user_id` 隔离）。

`messages` 里的一条消息大致长这样：

```json
{
  "role": "user",
  "content": "帮我总结这份报告",
  "attachments": [
    {
      "id": "uuid",
      "name": "report.pdf",
      "mimeType": "application/pdf",
      "size": 123456,
      "kind": "document",
      "extractedText": "……",
      "truncated": false
    }
  ]
}
```

注意**附件内容也存在 jsonb 里**：文档类型存的是抽取出的正文（上限 12000 字），图片类型存的是模型服务的 `fileId`（图片本体在模型服务侧，不在你的库里）。

### 2.3 `shared_conversations`（分享快照）

完整定义见 `supabase/migrations/create_shared_conversations.sql`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `token` | text，主键 | 128bit 随机值（32 位十六进制），不可枚举 |
| `user_id` | uuid | 默认 `auth.uid()`，`on delete set null` |
| `title` | text，默认 `'共享会话'` | 会话标题 |
| `project_name` | text | 所属项目名（冗余存一份，避免联表） |
| `messages` | jsonb，默认 `[]` | 创建时的消息快照 |
| `created_at` | timestamptz，默认 `now()` | 分享时间 |
| `expires_at` | timestamptz，可空 | 预留的过期时间字段（当前代码未使用） |

### 2.4 `user_model_configs`（用户模型配置）

完整定义见 `supabase/migrations/create_user_model_configs.sql`。每个账号一行，整份模型配置存成一个 jsonb：

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | uuid，主键 | 默认 `auth.uid()`，`on delete cascade` |
| `profiles` | jsonb，默认 `[]` | 模型条目数组，**含各条目的 API Key** |
| `default_id` | text，默认 `''` | 默认条目 id |
| `selected_id` | text，默认 `''` | 上次选中的条目 id |
| `updated_at` | timestamptz，默认 `now()` | 最近一次同步时间 |

用「一行 jsonb」而不是「一条模型一行」，是因为客户端本来就把 `{ profiles, defaultId, selectedId }` 当整体读写，结构一一对应。

> **注意**：`profiles` 里含 API Key，这张表的数据等同用户凭据。RLS 只允许本人读写，**不要**给匿名读权限。未登录时配置只存在本机 `localStorage`，登录后才会上传。

## 3. RLS（行级安全）

业务读写用的是 **anon key**（公开值）+ 用户 access token，所以"数据隔离"这件事完全依赖数据库 RLS，而不是应用代码。策略写在库里，不在代码里。

`shared_conversations` 的策略在本仓库迁移脚本中明确定义：

```sql
-- 只读分享：任何人均可通过 token 读取（随机 token 不可枚举）
create policy "shared_select_anyone" on public.shared_conversations
  for select using (true);

-- 仅本人可创建自己的分享
create policy "shared_insert_own" on public.shared_conversations
  for insert with check (auth.uid() = user_id);

-- 仅本人可撤销（删除）自己的分享
create policy "shared_delete_own" on public.shared_conversations
  for delete using (auth.uid() = user_id);

-- 仅本人可更新自己的分享（例如修改过期时间）
create policy "shared_update_own" on public.shared_conversations
  for update using (auth.uid() = user_id) with check (auth.uid() = user_id);
```

设计取舍：分享页**不需要登录**，因此 `select` 放行所有人，安全性靠"token 不可猜"。这意味着拿到链接的人都能看，且链接不会过期（`expires_at` 目前没用上）。

`user_model_configs` 则相反，最严格——一条 `for all` 策略把四种操作全锁到本人：

```sql
create policy "model_config_own" on public.user_model_configs
  for all using (auth.uid() = user_id) with check (auth.uid() = user_id);
```

因为这张表存了用户的模型 API Key，任何越权读都等于泄漏凭据。

## 4. 持久化策略（重要，影响数据安全）

渲染端的读写封装在 `src/renderer/src/lib/persistence.ts`，其中写操作是**整表替换**：

```
1. DELETE conversations WHERE id <> ''   -- RLS 保证只删到自己的行
2. DELETE projects      WHERE id <> ''
3. INSERT 全部 projects（带 sort_order = 数组下标）
4. INSERT 全部 conversations
```

配合两个前端行为：

- **600ms 防抖**：任一状态变更后等 600ms 才落库（`persistTimerRef`），避免流式输出时高频写库。
- **首次跳过**：`skipPersistRef` 初值 `true`，挂载后的第一轮回写会被跳过，防止"数据还没加载完就被空数组覆盖"。

`user_id` 不写入请求体，靠数据库列的默认值 `auth.uid()` 自动归属当前登录用户。

内存模式（`store === "memory"`）下，既不会调用 `loadChatState`，也不会调用 `saveChatState`，数据只活在组件 state 里。

### 由此带来的已知限制

| 现象 | 原因 |
|---|---|
| 多设备/多标签页同时使用会互相覆盖 | 整表替换 + 无并发控制。设备 A 保存后，设备 B 的旧状态再保存就会把 A 的改动抹掉 |
| 没有 Realtime 同步 | 未订阅 Supabase Realtime，另一端的改动要刷新才可见 |
| 会话列表很大时保存变慢 | 每次保存都全量 delete + insert，没有增量更新 |
| 消息体很大时写库压力大 | 整条会话（含附件正文）都在一个 jsonb 字段里 |

如果后续要做"多人协作/大历史"，这里的改造点是：改成按行 upsert + 软删除，并引入 Realtime。

## 5. 认证流程

```
未配置 Supabase          → Onboarding（可进内存模式）
配置了但未登录           → Login（邮箱 + 密码）
   注册 → signUp() → 若返回无 session（开了邮箱验证）→ 提示去邮箱验证
   登录 → signInWithPassword()
   成功 → App 的 onAuthStateChange 收到事件 → user 非空 → 渲染 Chat
退出登录                 → supabase.auth.signOut()（在设置面板账号区）
```

- 会话默认持久化到 `localStorage` 并自动续期（`supabase-js` 默认行为），与网页端一致。
- 错误码到中文文案的映射是共享的：`src/shared/bridge-api.ts` 里的 `AUTH_ERROR_MESSAGES` + `humanizeAuthError()`。

### 会话有效期（不让它一直挂着）

Supabase 的 refresh token 默认会**无限续期**，只要客户端还在跑，会话就永不过期。所以应用层额外加两道限制，实现在 `src/renderer/src/lib/session.ts`：

| 限制 | 阈值 | 行为 |
|---|---|---|
| 空闲超时 | 连续 30 分钟无操作 | 清掉会话计时并 `signOut()`，回到登录页 |
| 绝对上限 | 从登录算起满 7 天 | 同上（无论是否活跃） |

- 活跃判定绑在 `mousedown / keydown / wheel / touchstart / focus` 上，写入有 30 秒节流，不会拖慢交互；
- 计时记录存 `localStorage`（`deekai:session`）。刷新页面**沿用**原记录（不会重置 7 天上限），主动退出登录才清除；
- 到期后登录页会显示「长时间未操作，登录已自动退出」或「登录已超过 7 天，请重新登录」。

**服务端兜底**：网页后端的 `/api/chat` 与 `/api/upload` 需要 `Authorization: Bearer <access_token>`，
服务端拿 anon key 去 Supabase 校验这个 token（`src/backend/supabase-auth.ts`），过期/伪造一律 401。
所以即使前端限制被绕过，token 本身失效后也调不动模型。未配置 Supabase（纯内存模式）时不启用鉴权。

> 想更严格可以在 Supabase 控制台调小 Auth 的 JWT 过期时间；但客户端会自动续期，
> 真正决定"能不能一直登录"的是上面这套应用层限制 + 服务端校验。

### 本机数据也按账号隔离

主题、侧栏折叠是全局的；但**头像**与**模型条目**都以用户 id 分键，同机多账号互不可见、互不覆盖：

| 数据 | `localStorage` key |
|---|---|
| 头像 | `deekai:avatar:<userId>`（未登录是 `deekai:avatar:local`） |
| 模型条目 | `deekai:models:<userId>`（未登录是 `deekai:models:local`） |

- 模型条目结构：`{ profiles: ModelProfile[], defaultId, selectedId }`，`ModelProfile` 含 `apiKey`。
- **登录后会同步到云端**（表 `user_model_configs`），所以同一账号换设备/换端也能拿到同一份配置；本机 `localStorage` 同时留一份做即时可用与离线兜底。
- 同步规则见 `syncModelStore()`：云端还没有记录就把本机这份上传；登录前在登录页配的匿名条目（`deekai:models:local`）会并进来，不会白配；云端有记录则以云端为准（避免旧缓存把已删除的条目"复活"）。
- 退出登录、关闭应用都不会清除本机那份，只有主动删除条目或点「清除本机设置」才会没。
- 未登录（或未配置 Supabase）时只用本机那份；网页端与桌面端、不同端口/域名属于不同 origin，`localStorage` 互不相通（开发时 `vite.web.config.ts` 已开 `strictPort`，避免端口漂移导致存储"换域"）。

## 6. 老数据认领（adoptOrphanRows）

这是唯一的"系统级"数据操作，位于 `src/backend/supabase-admin.ts`，两端都暴露（IPC `supabase:adopt` / `POST /api/auth/adopt`）。

**背景**：早期版本的 `projects` / `conversations` 没有 `user_id`，加上 RLS 之后这些历史数据变成"孤儿行"（`user_id is null`），谁都看不到。

**规则**：
1. 取当前用户 token 建一个 scoped 客户端，统计自己的 `conversations` 条数；
2. **只有当这个用户一条会话都没有时**才继续（避免覆盖已有数据）；
3. 需要有 `SUPABASE_SERVICE_ROLE_KEY`（没配就直接放弃）；
4. 用 service_role 客户端把 `user_id is null` 的行批量归到该用户名下：`update({user_id}).is("user_id", null)`；
5. 失败静默返回 `{adopted: false}`，不影响正常使用。

**触发时机**：渲染端在登录后，若该用户 id 不在本次会话的 `adopted` 集合中，就调一次（`api.adoptOrphans`，fire-and-forget，用当前 session 的 access token）。即**每个用户每次启动最多触发一次**。

配置要求见 [04-配置体系与版本.md](./04-配置体系与版本.md)：桌面端发行版**不需要**填 service_role key，只有网页后端或自托管时才需要。

## 7. 数据迁移与初始化清单

部署到一个全新 Supabase 项目时，需要：

1. **建表**：`projects`、`conversations`（字段见 §2，注意 `user_id` 列默认值设成 `auth.uid()`），并开启 RLS、按 `auth.uid() = user_id` 建 select/insert/update/delete 四条策略。
2. **执行仓库里的迁移脚本**（Supabase SQL Editor 或 CLI 跑一遍）：
   - `supabase/migrations/create_shared_conversations.sql`（会话分享）
   - `supabase/migrations/create_user_model_configs.sql`（用户模型配置云端同步）
3. **开启邮箱密码登录**：Supabase 控制台 → Authentication → Providers 里启用 Email；是否要求邮箱验证由你决定（客户端两种情况都处理了）。
4. **把 URL 与 anon key 写进配置**（`app-config.json` 或 `.env`），见下一篇。
