# 01 · 架构原理

## 1. 核心命题

同一个产品要跑在两个完全不同的环境里：

| | 桌面端 | 网页端 |
|---|---|---|
| UI 运行在 | Electron 渲染进程 | 浏览器 |
| 谁调模型 API | Electron 主进程（Node） | 你的 Node 服务 |
| 谁解析上传文件 | Electron 主进程（Node） | 你的 Node 服务 |
| 密钥存在哪 | 本机 `config.json` / 打包内置 | 服务端 `.env` / `app-config.json` |
| 数据持久化 | 渲染进程直连 Supabase | 渲染进程直连 Supabase |

注意最后一行：**数据读写两端完全一样**，都是浏览器/渲染进程拿着 `anon key + 用户 token` 直连 Supabase，靠数据库 RLS 做隔离。真正需要"服务端"的只有三件事：调模型、解析文件、用 service_role 做一次性系统操作。

于是架构被切成三块：

```
┌──────────────────────────────────────────────────────────┐
│  renderer（React UI）—— 两端完全共用同一份源码             │
│     只通过 lib/api.ts 这一个门面发起调用                    │
└───────────────────────┬──────────────────────────────────┘
                        │  DeekaiBridge 接口（src/shared/bridge-api.ts）
        ┌───────────────┴───────────────┐
        │                               │
  桌面端：preload/IPC           网页端：HTTP + SSE
  window.deekai                 fetch /api/*
        │                               │
  src/main/ipc.ts               src/server/router.ts
        └───────────────┬───────────────┘
                        │
              src/backend/*（纯 Node 逻辑，无框架依赖）
              deepseek.ts / uploads.ts / supabase-admin.ts
```

## 2. 三进程模型（Electron）

| 进程 | 文件 | 职责 | 权限 |
|---|---|---|---|
| 主进程 main | `src/main/*` | 窗口管理、配置读写、协议注册、调模型、解析文件、导出 PDF | 完整 Node 能力、能读密钥 |
| 预加载 preload | `src/preload/index.ts` | 用 `contextBridge` 把受控 API 挂到 `window.deekai` | 介于两者之间，唯一桥梁 |
| 渲染进程 renderer | `src/renderer/src/*` | 全部 UI 与业务状态 | 无 Node 能力，拿不到密钥 |

窗口创建时开启 `contextIsolation: true`、`nodeIntegration: false`（`src/main/index.ts`），渲染进程只能看到 preload 明确暴露的方法。

**密钥边界**：`DEEPSEEK_API_KEY` 与 `SUPABASE_SERVICE_ROLE_KEY` 只在主进程内被读取，从不进入 `PublicConfig`，因此渲染进程无论如何都拿不到。

## 3. 桥接适配器：UI 如何做到"不感知形态"

契约定义在 `src/shared/bridge-api.ts` 的 `DeekaiBridge` 接口：

```ts
export interface DeekaiBridge {
  kind: BridgeKind;                 // "desktop" | "web"
  getConfig(): Promise<PublicConfig>;
  saveConfig(values: WritableConfig): Promise<{ ok: true }>;
  chatStart(payload): Promise<void>;
  chatAbort(id: string): void;
  onChatEvent(cb): () => void;
  uploadFile(input): Promise<UploadedAttachment>;
  adoptOrphans(token, userId): Promise<{ adopted: boolean }>;
  openExternal(url: string): void;
  clipboardWrite(text: string): Promise<void>;
  openDesktop(payload: DesktopDeeplink): void;
  onDeeplink(cb): () => void;
  getPendingDeeplink(): Promise<DesktopDeeplink | null>;
  exportPdf(input): Promise<ExportPdfResult>;
}
```

两种实现：

- **桌面端**：`src/preload/index.ts` 实现该接口，每个方法转发到 `ipcRenderer.invoke/send`，主进程在 `src/main/ipc.ts` 注册对应 handler。
- **网页端**：`src/renderer/src/lib/bridge/http.ts` 实现该接口，走 `fetch("/api/...")`。

选择逻辑极简（`src/renderer/src/lib/bridge/index.ts`）：

```ts
export const bridge: DeekaiBridge = getElectronBridge() ?? httpBridge;
```

即"`window.deekai` 存在就是桌面端，否则用 HTTP"。UI 通过 `lib/api.ts` 调用，通过 `api.bridgeKind` 判断是否需要显示"在桌面端打开"这类入口。

### 两端行为差异（必须知道）

| 方法 | 桌面端 | 网页端 |
|---|---|---|
| `chatStart` 事件来源 | 主进程直连模型，用 IPC 推送 | 自己的后端返回 SSE，前端解析 |
| `exportPdf` | 弹保存框 → 隐藏窗口 `printToPDF` → 落盘，返回 `{saved:true, path}` | 打开新窗口写 HTML → `window.print()`，由用户"另存为 PDF"，不返回 path |
| `openDesktop` | 仅聚焦自身窗口（`window:focus`） | 拼 `deekai://open?...` 并跳转，唤起已安装的桌面端 |
| `onDeeplink` / `getPendingDeeplink` | 真实接收协议唤起事件 / 消费启动缓存参数 | 空实现，恒返回 `null` |
| `openExternal` | `shell.openExternal`（仅放行 http/https） | `window.open(url, "_blank", "noopener,noreferrer")` |

## 4. 能力后端分层：为"以后自己写 Java 后端"留的门

`src/backend/` 是**不依赖任何 Web 框架**的纯 Node 逻辑：

| 文件 | 职责 |
|---|---|
| `deepseek.ts` | 组装消息 → 请求 `{baseUrl}/chat/completions` → 解析 SSE → 产出 `ChatStreamEvent` 流 |
| `uploads.ts` | 图片走模型服务 Files API；PDF/DOCX/文本本地抽文本（上限 12000 字） |
| `supabase-admin.ts` | 老数据认领（service_role，一次性系统操作） |

上层有两个**薄适配器**，都把同一份 backend 逻辑暴露出去：

- `src/main/ipc.ts` → IPC 通道
- `src/server/router.ts` → HTTP 端点

`src/server/router.ts` 文件头直接写明了这套 HTTP 契约：

```
GET  /api/config          -> PublicConfig（公开配置，不含模型 Key / service_role）
PUT  /api/config          -> { ok: true }      请求体 WritableConfig，空串表示清除该键
POST /api/chat            -> text/event-stream，每帧 `data: <ChatStreamEvent JSON>`
                             请求体 { id, messages, profileId }；客户端断开即中止上游请求
POST /api/upload          -> UploadedAttachment  multipart/form-data，字段名 file + profileId
POST /api/models          -> { models, error? }  请求体 { baseUrl?, apiKey?, profileId? }
POST /api/auth/adopt      -> { adopted: boolean }  请求体 { token, userId }
```

**结论**：只要任何语言实现这 6 个端点，前端零改动即可切换后端。这就是"后端的相关逻辑需要明确分开"的落地方式。

注意"模型"是通过 **`profileId`** 传递的，不是模型名。配置层（`src/shared/config-core.ts` 的 `resolveModel()`）负责把 `profileId` 解析成 `ResolvedModel{ baseUrl, model, apiKey, supportsFiles, visionModel }`，能力层不认识厂商、也不读配置文件。这样以后加 MCP / 智能体之类的扩展，只需在配置层多解析一层，backend 与 UI 的接口形状不用变。

## 5. 启动流程

### 5.1 桌面端（`src/main/index.ts`）

1. 非打包运行时把 `userData` 改到项目内 `.dev-profile`（避免写系统目录受阻）。
2. `app.requestSingleInstanceLock()` 取单实例锁，拿不到直接 `quit()`。
3. `app.whenReady()` 后依次：
   - `configManager.load()` —— 读发行内置配置、`.env`、环境变量、用户 `config.json`；
   - `registerIpcHandlers()` —— 注册全部 IPC；
   - `registerProtocolClient()` —— 注册 `deekai://` 协议（Windows 写 `HKCU\Software\Classes\deekai`）；
   - `createWindow()` —— 1280×820 窗口，`show:false` 等 `ready-to-show` 再显示；
   - 从 `process.argv` 提取 `deekai://` 链接（Windows 首次通过协议启动的场景）。
4. `second-instance` 事件（协议再次唤起）→ 提取链接 `emitDeeplink()` + 聚焦窗口。
5. `window-all-closed` → `abortAllStreams()` 中止所有在跑的流，非 macOS 退出。

外部链接策略：`setWindowOpenHandler` 与 `will-navigate` 都把 http/https 交给系统浏览器，应用内不做跳转。

### 5.2 渲染端（`src/renderer/src/App.tsx`）

App 是一个状态机，按以下优先级决定渲染什么：

```
if (shareToken)                    → 只读分享页 SharedView（无需登录）
else if (!config)                  → 启动屏（转圈 + "DeekAI 正在启动…"）
else if (config.supabaseConfigured)
     ├─ 已登录                     → <Chat userId store="supabase">
     └─ 未登录                     → <Login>
else if (!memoryMode)              → <Onboarding>（引导配置 / 内存模式试用）
else                               → <Chat userId={null} store="memory">
```

配置加载成功后：若 Supabase 配齐则 `initSupabase(url, anonKey)`，随后用 `getSession()` + `onAuthStateChange()` 驱动登录态。设置面板 `onSaved` 回调会 `window.location.reload()`，强制重建 Supabase 客户端与门控视图。

分享路由是纯 hash 路由，正则 `^#\/share\/([A-Za-z0-9_-]{8,})` 匹配 `#/share/<token>`，因此桌面端 `file://` 与网页端都能用同一个链接地址打开。

## 6. 一次完整对话的数据流（桌面端）

```
用户按 Enter
  → Chat.send()：组装 user 消息 + 附件，写入会话，追加空的 assistant 占位
  → api.streamChat(history, profileId, onDelta)
       ├─ 生成 id = crypto.randomUUID()
       ├─ bridge.onChatEvent(handler)   ← 订阅（单订阅者模型）
       └─ bridge.chatStart({id, messages, profileId})
            → IPC "chat:start"
            → 主进程 configManager.resolveModel(profileId)
                 ↳ 解析出 { baseUrl, model, apiKey, supportsFiles, visionModel }
            → 建 AbortController 存入 activeStreams
            → backend/deepseek.streamChat({ profile, messages })
                 ├─ 有图片附件且条目声明了视觉模型 → 改用 visionModel
                 ├─ supportsFiles 为真才把图片作为 file_id 内容块发上去
                 ├─ 文档附件 → 拼进文本上下文
                 ├─ fetch POST {baseUrl}/chat/completions (stream:true)
                 └─ 逐行解析 SSE，emit(delta) → win.webContents.send("deekai:chat")
  ← preload 的 ipcRenderer.on("deekai:chat") 转发给 handler
  ← handler 按 event.id 过滤，delta 回调累加文本并 setAssistantContent
  ← done → resolve；error → reject；stopped → reject AbortError
  → finally: setStreaming(false)，abortRef = null
```

停止生成：点「停止」→ `abortRef.current.abort()` → `chat:abort` → `controller.abort()` → 上游 fetch 抛 `AbortError` → emit `stopped`。

网页端链路一致，只是把 IPC 换成 `POST /api/chat` + SSE 读流；客户端断开（关页面/点停止）时 `res.on("close")` 会中止上游请求，避免白跑 token。

## 7. 安全边界小结

| 项 | 处理方式 |
|---|---|
| 运营方模型 Key（`DEEPSEEK_API_KEY` 等） | 只在主进程 / 服务端存在；渲染进程只能拿到 `serverModelProfiles` 里的 `hasKey` 布尔值 |
| 用户自己的模型条目 | 未登录存本机 `localStorage`；登录后同步到 Supabase `user_model_configs`（RLS 仅本人可读写）。调用时随请求以 `inline` 目标带给后端，**后端只转发不落盘** |
| 登录会话 | 应用层限制：空闲 30 分钟 / 累计 7 天自动登出（`lib/session.ts`）；网页后端对 `/api/chat`、`/api/upload` 校验 access token，无效返回 401 |
| Supabase `anon key` | 视为公开值（与网页端一致），靠 RLS 隔离数据 |
| Supabase `service_role key` | 只在后端，仅用于"老数据认领"这一件事 |
| 页面安全 | `index.html` 里声明 CSP，限制 `script-src 'self'`、`img-src 'self' data: blob: https:`、`connect-src` 白名单 |
| 外链 | 只放行 `^https?://`，一律交给系统浏览器 |
| 分享链接 | token 为 128bit 随机十六进制（32 字符），不可枚举；只读快照 |
